# DM Tools

DM Tools is the planning and world-building addon for
[ttrpg-codex](https://github.com/pjunak/ttrpg-codex). It gives an effective DM
three views over one shared model:

- a manual workspace for story threads, quests, situations, encounters, notes,
  folders, named sections, and named semantic links;
- a draggable campaign graph with saved positions, a selected-node inspector,
  and explicit named connections between plans, NPCs, and other world
  entities;
- a reviewed Import Center for larger structures generated by a person or an
  LLM.

It contributes the normal planning overview to the host-owned `/dm` dashboard.
It does not depend on Character Sheets or the 2024 Compendium, and those addons
do not depend on it.

## Data contract

All addon collections are host-managed and DM-only:

| Collection | Shape | Purpose |
|---|---|---|
| `planning_items` | keyed | Threads, quests, situations, encounters, and notes. |
| `planning_folders` | keyed | Navigation only. |
| `planning_links` | keyed | Named semantic connections between planning sections, core entities, and optional external-addon records. |
| `planning_views` | keyed | Presentation-only graph positions. It never changes planning meaning or import data. |
| `scenarios` | list | Retained legacy source; startup copies compatible records non-destructively into `planning_items`. |

Core entity reads are limited to characters, factions, locations, mysteries,
artifacts, and events so those records can participate in named links without
being duplicated.

The manual workspace and the import provider validate against the same
[`planning-contract.js`](planning-contract.js). Import details are in
[`docs/IMPORTING.md`](docs/IMPORTING.md). Agents generating planning documents
must follow [`docs/AGENT_GENERATION.md`](docs/AGENT_GENERATION.md).

## Routes

- `#/dm-plans` — manual planning workspace
- `#/dm-scenarios` — planning graph (the stable route name is retained)
- `#/dm-import` — reviewed bulk import
- `#/dm` — host-owned DM shell containing the addon dashboard

Only an effective DM registers these surfaces. Player, anonymous, and
DM-view-as-player payloads do not expose the collections or addon UI.

The planning workspace keeps item selection and editing separate: the
filterable folder list remains a compact navigation column, while folder
administration is collapsed until needed. All planning and connection fields
remain native labelled controls so the same workflow works without the graph.

## Import and graph guarantees

The provider `(dm-tools, planning-json)` uses provider API 1 and planning schema
version 1. Preview is read-only. Commit uses the exact server-held plan and
publishes at most 256 writes through one atomic host transaction. Updates
require the current `updatedAt`; conflicts never overwrite.

The same provider is registered as the restricted campaign-bundle contributor
`(dm-tools, planning)`. A host campaign bundle can therefore create core NPCs
or locations and DM-only planning records in one reviewed publication. Exact
`{"$ref":"..."}` objects inside the nested planning document resolve to IDs
reserved by the host preview; DM Tools still returns writes only for its own
planning collections and never receives core-write authority.

The graph is a projection of stored records only. A link's fixed type supports
consistent semantics and its custom name is the visible edge label. A link to
a named section rolls up to the parent item while collapsed and resolves to
the exact section node while expanded. Dragged positions are stored separately
in `planning_views`; resetting the arrangement cannot alter any item, section,
folder, or link. See [`docs/GRAPH.md`](docs/GRAPH.md).

## Test and install

From this repository:

```powershell
node --test tests\*.mjs
```

From the sibling host repository:

```powershell
node scripts\dev-install-addon.cjs ..\dm-tools
```

Manifest permission changes require the per-addon installation wizard in
production. Server-provider changes require reinstall, host restart, and
browser refresh.
